WORKING OF JOINS

Spark internally shuffles matching data from nodes to nodes based on col_name

broadcast_join()  -> Instead of shuffling large dataframe across nodes (which is costlier), 
spark send small df to all nodes and performs join

df_large.join(broadcast(df_small) on='col_1', how='inner').show()
----------------------------------------------------------------------------------------------

explode() and explode_outer() -> returns each element in items_array as new row

df.withColumn('items', explode(col('items_array'))).show()
df.select('items_array', explode(col('items_array')).alias('items')).show()

explode excludes null items_array
explode_outer() includes null items_array

IMP :- explode() takes only array or map columns but not struct columns {x,y,z}

PIVOT :- The distinct values in pivot_column becomes columns

df.groupBy('student').pivot('subject').agg(sum('score'))

EXPLANATION :- .groupBy() converts multiple rows of one student into one row/ student
               .pivot() converts all subjects into columns
               .agg(sum('score')) [mandatory with pivot]
-----------------------------------------------------------------------------------------------

DATA SKEW 

1. A partition has significantly more rows or data than others.

2. A partition has many rows with the same key/partition value, leading to uneven distribution.

Why it’s bad: Data skew is a performance killer. If one worker gets a large partition, it 
takes much longer to process compared to other workers. Even if the other workers finish quickly,
Spark must wait for the slowest (skewed) partition before sending results to the driver.

Fix the SKEW 1. repartition
             2. broadcast join
             3. Salting technique
